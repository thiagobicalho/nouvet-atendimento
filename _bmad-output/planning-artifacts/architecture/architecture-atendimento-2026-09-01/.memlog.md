- (constraint by thiago) Cofre de credenciais nativo do n8n (FR-43 do PRD) funciona normalmente em instancia self-hosted - nao e recurso Enterprise, confirmado via docs oficiais (docs.n8n.io/hosting/configuration/configuration-examples/encryption-key, docs.n8n.io/external-secrets). O que e Enterprise-only e 'external secrets' (puxar de vault externo tipo AWS Secrets Manager/HashiCorp Vault) - nao necessario aqui, o cofre nativo basta para FR-43.
- (constraint) Gotcha operacional real do n8n self-hosted: por padrao a N8N_ENCRYPTION_KEY e auto-gerada e salva em disco - se o volume nao for persistido ou o container recriado do zero, a key some e todas as credenciais salvas ficam ilegiveis permanentemente, sem rollback. Mitigacao: definir N8N_ENCRYPTION_KEY fixa via variavel de ambiente (minimo 32 chars hex/256-bit) antes do go-live, nunca deixar auto-gerar. Fonte: docs.n8n.io/hosting/configuration/configuration-examples/encryption-key.
- (decision by thiago) Topologia de banco confirmada com Thiago: um unico servidor Postgres na VPS, mas DUAS bases de dados separadas, cada uma com usuario proprio de privilegio minimo - (1) banco interno do proprio n8n (workflows/execucoes/credenciais, DB_TYPE=postgresdb apontando pra essa base, nao SQLite) e (2) banco dedicado da aplicacao (secretaria_config, secretaria_profissionais, n8n_historico_mensagens, n8n_fila_mensagens, n8n_status_atendimento), acessado via credencial Postgres propria dentro dos workflows do agente. Confirmado como best practice oficial do n8n (docs.n8n.io/hosting/configuration/supported-databases-settings - 'create a dedicated database and user for n8n... separate user with limited permissions'). Thiago vai configurar isso (encryption key fixa + as duas bases) na hora de subir a VPS.

- (decision by thiago) Identidade de cliente/pet: Postgres passa a ser a base operacional de identidade do Nouvet, alimentada por (a) importacao unica inicial da base atual do SimplesVet, e (b) novos cadastros criados direto no Postgres quando o agente identifica um cliente novo. O schema da tabela de identidade replica os mesmos campos que o cadastro do SimplesVet ja pede hoje (nome, contato, dados do pet). Isso substitui o fluxo de reimportacao periodica do SimplesVet - so precisamos de UM import inicial, dali em diante o caminho e o inverso.
- (decision by thiago) Sincronizacao Postgres -> SimplesVet: quando um cliente novo e criado no Postgres com simplesvet_status=pendente (ainda nao existe no SimplesVet), o fluxo cria uma TAREFA no card do RD Station CRM (usando o recurso nativo de Tasks da API do CRM, ja documentado na skill rd-station-api) pedindo que um humano cadastre esse cliente no SimplesVet. Etiqueta foi descartada como mecanismo (dependeria de humano lembrar de remover depois, risco de ficar esquecida).
- (decision by thiago) Papel do Postgres de identidade vs. card do RD CRM: confirmado que sao complementares, nao duplicados - Postgres resolve 'quem e esse telefone e qual o pet' (identidade operacional rapida, sem depender de SimplesVet nem de chamada de API toda hora); o card do RD CRM continua sendo 'onde essa pessoa esta no funil, o que esta sendo negociado' (FR-21 - cadastro definitivo so apos intencao confirmada). Postgres alimenta a decisao de criar/atualizar o card, nao substitui ele.
